# F2F Bank tests

В этом проекте я исследовала приложение F2F Bank и написала автотесты на Playwright.
Тесты покрывают основные UI-сценарии и API-сценарии: регистрацию, вход, переводы, баланс и транзакции.

## Запуск приложения

Из корня проекта:

```bash
docker compose up -d --build
```

Приложение открывается по адресу:

```text
http://localhost
```

## Запуск тестов

Из папки `tests`:

```bash
npx playwright test
```

Запуск только UI-тестов:

```bash
npx playwright test tests/ui
```

Запуск только API-тестов:

```bash
npx playwright test tests/api
```

Открыть HTML-отчет:

```bash
npx playwright show-report
```

## Структура

```text
tests/
    api/        API-клиенты
    fixtures/   общие фикстуры Playwright
    pages/      Page Object для UI-тестов
    tests/
        api/    API-тесты
        ui/     UI-тесты
```

Для тестов, где нужен авторизованный пользователь, используется `beforeEach`.
В нем создается новый пользователь и выполняется вход.
`storageState` не использовался, потому что для тестов баланса и транзакций удобнее каждый раз начинать с чистого пользователя.

## Покрытые UI-сценарии

### Регистрация

1. Регистрация нового пользователя
   - Входные данные: имя, фамилия, уникальный email, пароль.
   - Ожидаемый результат: пользователь создан, открывается страница логина.
   - Критичность: критический.
   - Тест: `register.spec.ts`.

2. Повторная регистрация с тем же email
   - Входные данные: один и тот же email используется два раза.
   - Ожидаемый результат: появляется ошибка `User with this email already exists`.
   - Критичность: высокий.
   - Тест: `register.spec.ts`.

3. Проверка обязательных полей регистрации
   - Входные данные: пустое имя, фамилия, email или пароль.
   - Ожидаемый результат: форма не отправляется.
   - Критичность: высокий.
   - Тест: `register.spec.ts`.

4. Регистрация с некорректным email
   - Входные данные: email без `@`.
   - Ожидаемый результат: форма не отправляется.
   - Критичность: высокий.
   - Тест: `register.spec.ts`.

## Покрытые API-сценарии

## Найденные дефекты и особенности

### Некорректный placeholder в поле пароля

Страница: `/register`

Фактический результат: в поле пароля отображается placeholder `Type your message...`.

Ожидаемый результат: placeholder должен быть понятным, например `Type your password`.

Критичность: низкий.

### API принимает некорректный email

Endpoint: `POST /api/auth/register`

Фактический результат: backend принимает email вроде `"123"` и возвращает `201`.

Ожидаемый результат: backend должен проверять формат email и возвращать ошибку.

Критичность: средний.

### Перевод не проверяет существование получателя

Страница: `/`

Фактический результат: перевод проходит на любой валидный по формату номер, если хватает баланса.

Ожидаемый результат: приложение должно проверять, что получатель существует.

Критичность: высокий.

### Ошибка загрузки баланса на странице логина

Страница: `/login`

Фактический результат: без авторизации появляется snackbar `Failed to load balance`.

Ожидаемый результат: страница логина не должна запрашивать баланс пользователя.

Критичность: низкий.

### Плохая читаемость текста на странице транзакций в темной теме

Страница: `/transactions`

Фактический результат: если включена темная системная тема, текст заголовка, таблицы и данных почти не виден на светлом фоне.

Ожидаемый результат: текст должен быть контрастным и хорошо читаться при любой системной теме.

Критичность: средний.
